# State Management

Обзор решений по управлению состоянием в проекте `task_03`

---

## 1. RTK Query — серверное состояние заказов

**Файлы:** `entities/order/api/index.ts`, `entities/order/api/hooks.ts`

**Что хранит:** список заказов с сервера, статусы загрузки и ошибки, кеш ответов.

**Где используется:**

- `useOrders()` из `hooks.ts` — обёртка над `useGetOrdersQuery` с централизованным `pollingInterval: 10_000ms` и
  `skipPollingIfUnfocused: true`; используется в `KanbanBoard` и `StatsPanel`
- `useUpdateOrderStatusMutation` в `OrderCard` — PATCH-запрос смены статуса заказа; RTK Query автоматически управляет
  флагом загрузки и инвалидирует кеш по тегам после успешной мутации

**Почему так:**
серверное состояние не должно дублироваться в Redux вручную. Два подписчика на `useOrders` (`KanbanBoard` и
`StatsPanel`) порождают один реальный HTTP-запрос — RTK Query дедуплицирует их. Полинг, инвалидация кеша через теги при
мутациях, `isLoading`/`isError` — всё это предоставляется библиотекой без написания дополнительной логики.

**Плюсы:**

- Единственный источник правды для серверных данных
- Полинг и инвалидация кеша без написания логики вручную
- `isLoading` / `isError` из коробки, не нужен локальный стейт
- Два подписчика — один запрос (дедупликация)

## 2. Redux Toolkit — глобальный UI-стейт фильтров

**Файл:** `features/stationFilter/model/slice.ts`

**Что хранит:** `selectedStation` (выбранная станция фильтра) и `showReadyOrders` (видимость колонки "Готово").

**Где используется:**

- `StationFilter` — читает оба значения, диспатчит изменения
- `KanbanBoard` — читает оба значения для фильтрации заказов и рендера колонок

**Почему так:**
оба значения нужны двум компонентам-сиблингам (`StationFilter` и `KanbanBoard`) без общего родителя кроме `App`. Prop
drilling через `App` возможен, но хрупок при росте дерева. Роутера в проекте нет, поэтому хранение `selectedStation` в
URL-параметрах потребовало бы ручной синхронизации.

**Плюсы:**
- Нет prop drilling через `App`
- Не требует роутера
- Redux DevTools, `preloadedState` в тестах

**Минусы:**
- Состояние сбрасывается при рефреше страницы

### Альтернатива: useContext
**Плюсы:**
- Для двух значений типа string | 'all' и boolean — Context более чем достаточно
- Нет overhead от Redux (actions, reducers, dispatch)

**Минусы:**
- Нет встроенной мемоизации (при изменении контекста ререндерятся все подписчики). Но можно разделить на два контекста
и использовать memo.

## 3. useState — локальный таймер в OrderCard

**Файл:** `entities/order/ui/OrderCard/OrderCard.tsx`

**Что хранит:** `waitMinutes` — время ожидания заказа в минутах, вычисляется из
`order.createdAt`.

**Как работает:** `setInterval` с интервалом пересчитывает значение каждые 30 секунд. Отображаемое число
`displayMinutes = Math.floor(waitMinutes)` меняется визуально максимум раз в минуту — при пересечении целой минуты.

**Почему так:**
Это полностью локальное UI-состояние одной карточки. Никакой другой компонент не должен знать отображаемое время
конкретного заказа. `useState` — единственно верный выбор для изолированного, недолгоживущего состояния.

**Плюсы:**
- Полная изоляция внутри компонента
- Не расширяет глобальный стор

**Минусы:**
- Каждая карточка держит свой `setInterval` — при большом количестве заказов множество независимых таймеров, но в нашем
случае не предполагается большого количества карточек
